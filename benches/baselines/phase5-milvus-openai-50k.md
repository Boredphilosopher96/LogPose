# Phase 5 Milvus Comparison: openai-50k

Generated by `scripts/bench-milvus.sh`; do not edit by hand. See `benches/baselines/README.md` for how to read it.

**Synthetic data.** 50,000 vectors of 1536 dimensions and 1,000 queries, cosine metric, from the embedding-like generator (32 latent dimensions, 256 clusters, seed 42). It mirrors only the shape of VectorDBBench OpenAI 50K (1536 dims, cosine); the public VectorDBBench files were not reachable.

Recall is mean recall@10 against exact ground truth. Each system's `ef` is the smallest swept value with recall of at least 0.95.

## Caveats

- These results do not show that the Phase 5 exit criterion is met. That needs Cohere 1M, OpenAI 500K, and a 10M case on the public datasets, on a quiet machine.
- LogPose ran its pre-v2 query planner. Rerun after planner v2 lands.
- LogPose's compaction stopped short of one segment (see `server_stats`), and segments under 20,000 rows have no graph and are scanned exactly. Every query searches every segment and merges.
- The machine was busy with other work: the 1-minute load average was 12.1 when LogPose started, 11.9 when Milvus started, on 4 logical CPUs. The two systems did not see the same contention, so neither the absolute numbers nor their ratios are what either system reaches on a quiet machine.
- LogPose is driven by a Rust gRPC client and Milvus by `pymilvus`, one Python process per client. Every client runs on the same machine as the server and takes CPU from it.
- The vectors are synthetic, so recall and speed may differ on the public datasets.
- Corrected after the run: the LogPose driver recorded the requested `ef` (16), but LogPose raises every `ef` to its floor of 4 * k = 40 candidates, so every LogPose row ran at 40. The LogPose `ef` values in the JSON file now say 40; no measurement changed. `vdb-run` now records the `ef` that ran.
- Recorded after the run: Milvus searches used consistency level Bounded, the level `pymilvus` 3.0.2 gives a new collection when none is named (the driver now sets it explicitly). Every row was flushed and indexed before the first search, so every search saw all rows.
- Provenance: the LogPose binaries were built from commit `eb8dbbf` plus the insert-retry change later committed as `855bee0`. The `git_commit` in each report names whatever `HEAD` was checked out when it was written, and the tree was dirty.

## Notes

- LogPose: recall is mean recall@k against exact ground truth computed by logpose-bench vdb-prepare
- LogPose: latency is measured by the client around each gRPC call, so it includes serialization and loopback transport
- LogPose: each concurrent client has its own gRPC connection and runs in the driver's tokio runtime on the same machine as the server
- LogPose: LogPose applies ef as max(ef, 4 * k) and widens it for filtered walks that come up short
- LogPose: the dataset is synthetic (embedding-like, see dataset.generator); it mirrors only the shape of the public dataset named in dataset.mirrors
- Milvus: recall is mean recall@k against exact ground truth computed by logpose-bench vdb-prepare
- Milvus: latency is measured by the client around each pymilvus search call, so it includes Python serialization and loopback transport
- Milvus: each concurrent client is its own Python process with its own connection, on the same machine as the server
- Milvus: searches use the collection's default consistency level; the scalar field has a STL_SORT index
- Milvus: the dataset is synthetic (embedding-like, see dataset.generator); it mirrors only the shape of the public dataset named in dataset.mirrors
